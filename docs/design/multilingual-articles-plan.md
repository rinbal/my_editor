# Multilingual articles: implementation proposal

Reviewed 2026-11-21, including an independent red-team/blue-team UX review. Status: revised design and implementation contract; no feature code or native UI validation yet. The UX rules below supersede the earlier batch-publication and root-only comparison proposals.

This hardens [STANDUP #116](https://github.com/DoktorShift/standup/issues/116) and its [research and concept](https://github.com/DoktorShift/standup/issues/116#issuecomment-6760859354). It covers MyEditor, STANDUP blogs, Discover and the existing submission path. Recommendations here remain proposals; they do not record owner approval of the issue's open decisions.

Initial inspection used older feature checkouts. The subsequent [coordinated integration plan](multilingual-integration-plan.md) reconciles current upstream: MyEditor `rinbal/dev` at `a88c403a4d4ce99cfc00874d33c5940e28530787`, STANDUP official main at `ebcfc35aa69474d37e353290dd9d1bc695240a27`. Use those verified bases, refreshed before implementation; the old submission/backend feature branches are historical ancestors.

## Product contract

An author writes one piece in several languages. Each version has its own document, publishing state and ordinary Nostr article. The apps connect them and choose a suitable version for listings. Readers can always choose another available version.

The everyday author flow is **Write in another language… → English → write → Publish English**. The language choice opens the document immediately. The entry label describes manual authorship; it must not imply machine translation. Existing articles gain one language field. Technical addresses, tag forms, group identifiers and relay coordination stay behind the interface.

### UX rules after adversarial review

- One setup choice: the language to write in. No wizard, source-version picker, copying preference, translator form, readiness toggle or payment decision.
- One fixed writing target. Selecting text in the reference never changes which document Publish will send.
- Publish sends the active language by default. A private reference stays private. Publishing several versions is a deliberate secondary action with an explicitly named scope.
- Reference language follows the version where the author started. Writing Spanish from English must not force comparison against a German root.
- Healthy documents show no translation-health badge. One relevant change hint and one recovery action are enough.
- Readers make no setup decisions. A suitable version opens from a grouped listing; a specific shared link keeps its language.

### Space for writing

The second UI pass removes duplication instead of reducing text or control sizes. The subsequent owner review removes the remaining language-only row entirely, in both editors. Use the same Languages icon beside Preview in the existing formatting toolbar; MyEditor's existing Nostr command remains an alternative entry point to that same chooser. Do not add a document/pane language strip. The reference has only a small inline caption when visible. Current language is available in the icon's accessible name/tooltip, the chooser, ordinary document context and the named Publish action.

Preview, Languages, reference visibility and Details use consistent icons and accessible names across the two products. On compact screens, secondary formatting commands fold into the existing formatting menu. The same Languages icon opens the reader's available published versions; cards show the icon plus an available-version count. Use a distinct globe for interface-language settings. Menus retain full recognizable language names. Never replace essential publication-scope text with an unexplained icon.

Details starts closed for a new translation and remembers the author's later choice. On desktop it temporarily uses the reference slot, so the body never competes with a reference and an inspector at once. In a narrow window it opens as a dismissible overlay. The reference defaults to approximately one third of the usable width, leaving the larger share for writing; retain readable minimum widths and the existing one-pane fallback. One close action hides it and one contextual Show action restores it.

MyEditor retains native document/window navigation and existing commands; do not reproduce the operating system's menu bar inside the window or add a translation toolbar. The standalone review represents native Nostr commands with one compact radio/menu icon. Standup consolidates its separate branding/page-heading/action bands into one editor header containing back navigation and essential actions. Remove the generic New Article/Article subtitle and the extra language row. Both products use the same Preview/Languages/reference/Details icon group; compact formatting commands and secondary actions stay available through their existing menus.

### Language choice is not a short whitelist

Keep a small recent-language palette when the chooser opens, but search the complete bundled language catalogue. The exported review includes 7,923 active registered language entries from the [IANA language-subtag registry](https://www.iana.org/assignments/language-subtag-registry/language-subtag-registry), snapshot File-Date 2026-11-18. Deprecated entries, collections, private-use ranges and non-language placeholder values are excluded. Registered historical languages remain searchable; an exact familiar match ranks first. The small palette never limits writing or publication.

Search localized/English names, native names, recognized aliases and internal codes. Thai/ไทย, Lao/ລາວ (also Laos/Laotian), Khmer/ខ្មែរ and Japanese/日本語 (also Japan) must work. A name/code is never a manual prerequisite for ordinary use: choose the named result and start writing. Use canonical language codes as identities, not localized display names; reopening an existing language retains its document. Keep existing/recent choices first, provide All languages and bounded result pages, and do not stretch the chooser into a page-length list. Search must respect IME composition and keyboard selection.

This catalogue is independent of the app's interface translations, spelling dictionaries, language detection, dictation and machine-translation services. Missing support in one of those optional facilities must not disable a writing language. Registered script/region variants are preserved, and existing variants remain directly selectable without an extra variant-configuration step. Verify Unicode input, shaping, combining marks, line wrapping, bidirectional content and font fallback in native Qt and browser acceptance.

The normal Publish review shows the title, reader-card preview, signing account and exact publication scope. Summary, hashtags, cover changes and credits remain editable behind Details. Do not repeat the already chosen language as another field in this review. The menu attached to the named Publish action holds Publish both; choosing it reveals both previews and changes the final button to name both languages. The default remains one version. Private-source disclosure, source-change review, cancellation and failure retry are never hidden with optional metadata.

The first coherent release includes language selection, linked drafts, comparison, reliable publication, reader switching, grouped cards, and preservation through the current editorial path. Grouped editorial inboxes, commissioning, group-aware curations and machine translation are later capabilities, still part of the issue's full acceptance scope.

## Findings that change the existing plan

| Finding | Consequence |
| --- | --- |
| Marked `a`/`e` tags are a precedent, not a translation standard. | Document `original`/`translation` as an application convention and verify client round trips before fixing the wire contract. |
| Two independently signed Nostr events cannot be published atomically. | One Publish sheet needs durable per-version progress and retry; partial success must be ordinary, recoverable behavior. |
| Adding a backlink changes the original event ID without changing its writing. | An `e` mismatch alone cannot justify an outdated warning. |
| The original's address includes the signer, which can be a publication account. | Group authorization uses signing keys and explicit relationships, never a credited author or translator. |
| `ArticleDetails.from_tags` rebuilds `p` tags and retains only the `author` role; the publisher also deduplicates people. | A proposed `translator` credit currently disappears on save, and overlapping roles need explicit publisher rules. Add role-aware preservation at both boundaries. |
| `nostr/standup/drafting.py::_work` puts only zap tags in `extra_tags`. | Translation provenance is currently lost on submission. Fix preservation in the first release, before a grouped inbox exists. |
| Current language readers collapse subtags and accept any two ASCII letters. | Introduce validated languages and separate exact identity from fallback matching; preserve imported subtags. |
| MyEditor's current Split mode is writing plus preview (`preview_pane.py`). | Comparing two article documents needs its own document binding and focus behavior. The existing preview split is not proof this is already supported. |
| #123 concerns publication home addresses. | Language-specific canonicals must use the same home-address resolver; multilingual code must not create a competing URL rule. |

## Red-team / blue-team UX disposition

Two independent reviewers challenged the initial plan, then tested the proposed remedies against private drafts, incidental reference focus and publication failure. This is an adversarial walkthrough of the design and existing UI code, not observed user research or an implemented UI test.

| Red-team objection | Blue-team response and final resolution |
| --- | --- |
| Setup becomes a form: source language, target language, blank/copy, credits. | Ask only the target language. Open the document immediately; existing Details holds optional metadata. |
| “Create translation” can promise generated text. | Use “Write in another language…” and the blank-state hint “Write or paste your English version.” Validate comprehension in the first-time walkthrough. |
| Publishing a translation can reveal a private original. | Default to active-language publication, retaining private linkage locally. “Publish both…” is a deliberate secondary action with named content review. |
| Clicking the source pane can retarget global Publish. | Keep the translation as the fixed target. Reference focus permits select/copy, with editing commands disabled where ambiguous. |
| A German group root forces a Spanish writer to work from German instead of English. | Automatically use the invoked English version as reference. Separate source provenance from group identity internally. |
| Batch rows, ready states and sibling checkboxes turn Publish into management. | Show one active version; show other versions only as relevant information. Pair review appears only after an explicit pair action. |
| Original edits create repeated review chores. | One passive change hint, no healthy-state badge, no required diff just to publish against a known older source. |
| Preview plus comparison creates three columns and duplicate view controls. | Reuse one supplementary pane; narrow reference navigation has one “Back to English” action. Respect deliberate hiding. |
| Failures produce a recovery wizard. | Reconcile uncertain outcomes automatically and retain one inline result with “Try again”. No surprise modal after restart. |
| Language badges become tiny targets and preference settings leak into reading. | One badge stack/control and one page-language menu; no reader setup. Page choice does not alter an explicit listing filter. |
| Later linking changes identities or lets one author conscript another's article. | Preserve established roots and version URLs; alias provisional singleton identities. Different signers require mutual signed evidence. |

The blue team's initial proposal still made publication of a private source a dependency. The final resolution adopts the red team's standalone-publication path instead. The protocol and index sections now account for its privacy and later-linking consequences; this is not an extra normal-user choice.

### Effort budget and first-time walkthrough

1. Choose **Write in another language… → English**. This is the only required setup choice; recent choices reduce searching and no extra Create button follows it.
2. Write or paste into English. Reference, inherited metadata and recovery are already in place. Translating the title can use the document's first heading; summary and translator credit are optional.
3. Choose **Publish English**, review the familiar sheet and publish. Default scope is always that document. A private source remains a draft without another question.
4. On failure, choose **Try again** once. The application identifies and retries the unfinished event; the author never chooses a relay, revision, group or recovery strategy.
5. A reader opens one suitable card and reads. A visible language menu is available only when another public version exists; switching language needs no preference confirmation.

Design targets: one required setup choice, one ordinary in-app publication review, zero reader setup, one recovery action. Existing external-signer authorization remains explicit and is not counted away to meet these targets. Pair publication and optional metadata are outside the default path. Verify first-time comprehension, wrong-document/publication mistakes, interruption count and recovery success in actual walkthroughs; no timing or success-rate claim has been measured yet.

## Protocol and research status

Keep one [NIP-23](https://github.com/nostr-protocol/nips/blob/master/23.md) kind 30023 event per version. Use an independent, stable `d` for every document MyEditor creates. Under [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md), replacement identity is `(kind, signer, d)`: equal `d` values across different signers do not replace one another. The stronger per-document uniqueness rule is a writer safeguard, not a protocol claim. Never regenerate a published address when its translated title changes.

[NIP-54](https://github.com/nostr-protocol/nips/blob/master/54.md) supplies a precedent for marked address and event references, specifically wiki forks. [NIP-84](https://github.com/nostr-protocol/nips/blob/master/84.md) illustrates contributor roles in highlights. Neither standard defines translation grouping for kind 30023. Treat our proposed markers and `translator` role as an explicitly documented convention using existing tag structures.

Initial candidate, on the English version:

```json
[
  ["L", "ISO-639-1"],
  ["l", "en", "ISO-639-1"],
  ["a", "30023:<root-signer>:<root-d>", "<relay-hint>", "original"],
  ["a", "30023:<source-signer>:<source-d>", "<relay-hint>", "source"],
  ["e", "<signed-source-version-id>", "<relay-hint>", "source", "<source-signer>"],
  ["p", "<translator-pubkey>", "<relay-hint>", "translator"]
]
```

The original may name an approved translation with `["a", "30023:<translation-signer>:<translation-d>", "<relay-hint>", "translation"]`. A same-signer translation need not require rewriting the original just to add this backlink. Discovery must query incoming `#a` references as well as outgoing references. Fetch candidate events, then validate markers and signatures locally; a relay's tag filter does not enforce our relation semantics.

The UX review separates group identity (`original`) from the version actually translated (`source`). This revises the earlier candidate's overloaded `e` marker; none of these markers is a shipped standard. When the reference is the root, both address references identify that same article. When translating an English version of a German article into Spanish, the root remains German while the source pair identifies the English revision. Validate the source revision and its confirmed group membership without recursively resolving every ancestor. Existing proposed root `e`/`original` pins may be read as legacy root-source provenance only after coordinate validation. The shared contract and client spike must cover both shapes before shipping.

Keep the existing [NIP-32](https://github.com/nostr-protocol/nips/blob/master/32.md) `ISO-639-1` labels for languages with those two-letter codes, including Thai `th`, Lao `lo`, Khmer `km` and Japanese `ja`. A valid registered language without a two-letter code, or a script/region-specific choice, uses the `lang` namespace with its BCP-47 identifier; never put a three-letter value into `ISO-639-1` or silently truncate it. NIP-32 permits application-defined namespaces. [PR #2451](https://github.com/nostr-protocol/nips/pull/2451) remains open and unmerged at review time, so describe this namespace as our documented interoperability convention, not an adopted Nostr language standard. Both writers, readers, editorial validators and expected-event builders must support this before offering the full catalogue in a production release. Define precedence for contradictory labels and preserve raw tags until explicit language correction. A valid `lang` value wins over a matching legacy base label; incompatible valid values yield an unresolved language rather than a tag-order-dependent answer. This requires no new article event kind.

The existing research's statement that NIP-90 inputs must be public is too broad: [NIP-90](https://github.com/nostr-protocol/nips/blob/master/90.md) includes encrypted inputs and results and is marked unrecommended. Exclude it from the initial feature because a human-authored workflow does not need it. A later translation service still needs explicit selection, disclosure of where draft text goes, and review before publication.

The issue's seven-client source audit is historical evidence from November 10. It is not fresh evidence of rendered behavior or safe re-saving. The implementation spike must record client version/commit, date, fixture and result for Pareto, Habla, YakiHonne, Highlighter, Primal, Damus and Amethyst. Distinguish article rendering, tag preservation on edit, and unsupported kind 30023. Read-only clients have no edit result. Use an authorized test identity and relays for live publication. No live events were published in this review. Do not advertise native translation support in those clients on the basis of ordinary article rendering.

## Group resolution and trust

1. Once a public group is confirmed, its immutable key is its root article's full address. Each variant retains its own address. The public root is a stable grouping anchor, not necessarily the language written first in private. A source language change never moves that identity. A standalone article has its own listing identity until confirmed group membership exists; that provisional singleton is not yet an immutable multi-version group.
2. Writers emit one root `original` address on a non-root version when that root is public and confirmed; the root does not reference itself. Readers allow a missing reciprocal reference when a valid root backlink establishes the relation, but never conflicting roots. Validate kind, public key, identifier, tag shape and signature. Reject self-reference, multiple conflicting roots, and cycles/chains in group-root declarations. The actual reference can be any confirmed version in that group; pin that signed source revision separately. Source provenance must not change group identity or require another choice from the author.
3. Confirm membership only when a verified relation connects the documents and either their signers match or both the target claims this root and the root's current verified event explicitly approves the target address. A root backlink alone can establish a same-signer relation if the other side lost its marker. A different signer's backlink alone cannot conscript an unrelated public article. A shared signer alone never groups unrelated writing, and matching the reference signer never bypasses a different root signer's approval. If every relation is stripped, recovery needs an explicit repair from retained provenance; it cannot be inferred safely.
4. An unrelated signer's unilateral claim remains an independent article with attribution. It cannot enter another author's switcher, card, SEO alternatives or group curation. Translator credit, matching titles, shared covers and publication placement confer no authorization.
5. Defer the proposed implicit approval through a blog list. It needs an exact signed schema, scope and revocation rule. The initial cross-signer path uses the root's explicit approval only. Reevaluate when an approval is removed; an unapproved article remains readable independently.
6. Keep all valid variants. Select at most one preferred public variant per exact language for grouped display: root itself for its language; otherwise an explicit, valid root preference if a future schema defines one; initially root-signer variants before approved external variants, then stable first-observed publication time, then full address as the deterministic tie-break. Missing or implausible `published_at` uses a persisted first-observed time. Store that resolved ordering consistently in the shared public index; do not let each browser recompute it. Do not discard the other articles.
7. Author-controlled timestamps must not confer trust. A duplicate same-language variant must not silently replace the author's open draft or a specifically requested article. The author flow opens the existing variant and offers an explicit separate-document action when appropriate.
8. Missing root, failed relay lookup, unconfirmed membership, deleted source and outdated translation are distinct states. An unresolved claim cannot hide an otherwise readable article. Previously verified membership may survive source deletion using retained signed evidence; a cold lookup with no evidence stays unresolved. Retain only the provenance needed, under existing data-retention rules.
9. A valid [NIP-09](https://github.com/nostr-protocol/nips/blob/master/09.md) deletion applies to the referenced author's own event or address. Deleting one version never sends deletion requests for its siblings. Surviving versions keep their URLs and group identity. Remove unavailable alternatives from public controls and SEO. If the root is deleted, choose a surviving version as the display fallback without changing the group key.
10. Bound relation lookups, candidate counts and relay work through existing lookup policies. Missing candidates never block opening the chosen article. Do not fetch every group separately on every card render.

The public index must store current event per address, root address, relationship evidence, membership state, exact language, preferred variant, source pin and freshness. Rebuild projections when content, relation, approval, language, deletion or placement changes. Backfill existing self-contained articles without guessing relationships from prose. Group IDs and version addresses remain separate fields in APIs and caches.

## Freshness that authors can trust

The `e` pin identifies the signed reference version actually used. Validate that the pinned event matches the declared source signer, kind and `d`, and that the source belongs to the confirmed group; an arbitrary event ID is not a source revision. Keep the verified source snapshot with the translation draft, encrypted through the existing draft path. A published pin references a public source revision, never an unpublished local draft. Private local relationships do not become public tags merely because their target is published.

Compare a versioned, deterministic projection of the pinned source with the current source: Markdown body, title, summary and exact language. Define missing values and Unicode/line-ending treatment in shared vectors before computing hashes. Exclude cover-only changes, backlinks, client tags, relay hints, credits and timestamps. A backlink-only rewrite therefore does not trigger a warning. A changed title or body does, conservatively including typo corrections. This is our application rule, not proof of semantic translation quality.

Freshness states are **matches source**, **source changed**, **cannot check**, and **source unavailable**. An absent historical source snapshot means cannot check, not outdated. A missing pin can remain a valid language alternative but has unknown freshness. Older revisions may no longer be retrievable from addressable-event relays, so do not make historical retrieval a prerequisite for reading.

Keep these technical states internal. Healthy documents show no status. A verified relevant change shows one passive line, “English version changed · Review”, naming the actual reference language. Review opens the difference; “Done reviewing” explicitly records the reviewed revision. Opening the difference alone, saving or publishing an unrelated edit must never advance the pin. Unknown or unavailable history belongs in Details unless it prevents a requested action. Keep hints within the relevant document; do not interrupt unrelated writing or turn each typo into a required review ceremony. Publishing against an older verified source remains possible with the change hint intact. A local reference change can be identified while drafting, but becomes public freshness evidence only after publication.

## Publishing and recovery contract

Prepare the explicitly approved publication scope and media before dispatch. Validate language, unique coordinates, signing authority, source pins, private-media handling and current remote revisions. Ordinary Publish sends one document. These internal checks do not create an additional user checklist or ask users to manage source revisions.

**Private-source rule:** publishing English while German remains private publishes an ordinary standalone English article with no private-source coordinates, revision pins, URLs or source text in its public metadata. Keep the relationship in encrypted/local provenance. The sheet says “English will be public. German stays a draft.” If a confirmed public root/reference already exists, include only those verified public relationships; an unavailable private reference never leaks through its tags. The reader sees a normal single-language article until public alternatives are confirmed. This path does not require publishing the source or repairing the group first.

If the original is published later, its normal review may include a backlink to an already public sibling recorded in the author's private relationship data. Show that existing sibling as information; do not re-sign or republish it. A valid same-signer backlink can establish the group. Without a public source pin, freshness stays unknown; a later explicit review/publication can add verified provenance. Different-signer publication still requires the sibling's signed root claim and the root's approval; show it independently until both exist, without demanding a linking task before publication.

Singleton promotion is an index operation, not an article-URL change. Preserve full-address permalinks, bookmarks and action targets; resolve previous singleton listing identities through an internal alias and preserve existing cursor snapshots until refresh. If the public English article already became the confirmed root for Spanish, later publishing the private German draft joins that established English-root group and never re-roots it. The public `original` marker identifies that stable anchor; source provenance remains separate. Choose the existing established group automatically from verified evidence. Conflicting established groups stay separate pending explicit advanced repair, rather than asking ordinary authors to choose a root or silently merging them.

**Pair rule:** “Publish both…” is a secondary action, never an automatic dependency escalation. Show both named versions and their content previews, say both become public, and use a named final button such as “Publish German and English”. Do not include unrelated unsaved source edits or substitute a different snapshot. If the source fails normal publication validation, point to that exact issue with “Open original”; the single-version route remains available without a new wizard. No sibling selection grid or extra confirmation after the ordinary final review.

For an explicitly selected new pair, establish stable addresses first. Build and sign the final original, including planned outgoing links, then build and sign the translation pinned to that exact source ID. Dispatch original before the dependent translation. If the reference snapshot and original proposed for publication differ, require review of that concrete difference before advancing the pin; never label an unreviewed translation as following the new text. A planned backlink to an unpublished event never becomes a visible language option until the target is verified and available. Same-signer additions can avoid a backlink rewrite altogether.

Use a durable operation record within the existing protected application storage. Record selected coordinates, source revisions, signed event IDs, dispatch state and existing publish-policy results per version. Reuse the application's publication acceptance policy and distinguish relay acceptance from later appearance in STANDUP or Discover. Do not claim every reader can already find an event after one acceptance.

| State | User-facing result and next action |
| --- | --- |
| Accepted | One short result, “English published” or “German and English published”. Per-version technical results stay collapsed. |
| Original accepted, translation failed | “German published. English couldn’t be published.” One “Try again” action retries only English; no recovery checklist. |
| Signer cancelled before dispatch | Preserve both drafts; no event has been sent. |
| Stopped after dispatch | Stop unsent work, reconcile any in-flight event and show the actual outcome. Use “Stop publishing” only while something can still be stopped; “Close” leaves already approved work running. No fictional rollback. |
| Timeout after sending | Reconcile the signed ID automatically with “Checking publication…”; users never decide whether an event probably published. Retry reuses the identical event where unchanged. |
| Restart during publication | Reconcile automatically. Restore one inline result/action in the relevant document or list; no unsolicited recovery modal or resumed new publication. Any unsent work needs a deliberate retry. |
| Source changed elsewhere | One passive “English version changed · Review” hint. Review is required to advance its pin or overwrite the source, not merely to publish against the older verified revision. |

Never re-sign an already successful version just because its sibling failed. Changed payloads create an explicit new revision; changed source pins require review. Before any existing-original backlink edit, refetch the current original and preserve unrelated changes. The relay protocol has no compare-and-swap guarantee: recheck immediately before dispatch, detect later divergence and recover visibly; do not promise that concurrent writes are impossible.

For an already published reference, the translation pins the version actually used, even when a newer version appears. The author may publish that older-source translation with the change hint; the app never substitutes the new source ID silently. Cross-signer approval updates are a separate recoverable publish step and never authorize overwriting another account's article. Closing a result keeps the work and its outcome available; there is no extra “Done” ceremony after success.

## Reader, listing and SEO behavior

Explicit article URLs always open their specific language version. Language preference applies when selecting a version for a group entry in a listing or a future group-aware curation. Choosing another language navigates to that version's stable URL with normal Back behavior; it does not silently rewrite a page's text or canonical.

Language choice: an explicit listing filter constrains eligibility; within it, use remembered reader choice, browser languages, blog default, available original, then a deterministic surviving fallback. Interface language is independent. Match exact language/script/region before a compatible fallback; never collapse distinct scripts into one selectable variant. An English-only filter includes only groups with an available matching English variant. A page-language choice remembers the preference for later unfiltered browsing but never rewrites an explicit listing filter. Browser Back restores the preceding page/list state. No preference prompt, cookie-choice-style language screen or language-change success toast.

Show one quiet Languages icon near article metadata only when a second confirmed, public version can be opened. Its menu uses full language names in their own language, with localized names where useful; the trigger's accessible name/tooltip includes the current choice. Never show placeholders for drafts, pending approvals, missing targets or failed publications. The public group projection renders the control without live relay lookups. Reader alternatives are the available published versions, never the entire authoring catalogue.

Following the owner's icon preference, cards use the shared Languages icon plus the available-language count at the end of the metadata row. Replace the bare DE/EN badge text with that one generously sized action. The article byline uses the same icon to open only confirmed published alternatives. Full names and the current choice remain in the menu and accessible names/tooltips. Single-language cards/articles show no language action. Keep interface-language settings distinct through the global globe icon. Keyboard and touch users receive the same information as hover users. Use measured semantic colors rather than hardcoded low-contrast grey.

Aggregate and filter groups before paginating: filtering two variants after fetching a page otherwise creates short pages, duplicates and wrong totals. Apply search matching to eligible variants before deduplication. For a query, choose a matching variant within the requested language rather than showing a preferred variant that does not contain the match; keep an explicit route to other versions. Define stable group ordering and cursor semantics so a metadata edit or a late translation does not unexpectedly jump a reader's position. Existing likes, comments, zaps and bookmarks retain their existing version-specific targets; do not combine counts or redirect payments to the root by inference.

Per-language feeds contain only available matching versions and retain each version's stable feed identity. An existing mixed feed remains mixed; do not change its meaning based on a viewer's remembered preference. A later group feed needs an explicit subscription format.

Each published version has its own canonical URL at the publication's configured home, through the shared resolver required by [#123](https://github.com/DoktorShift/standup/issues/123). Do not canonicalize translations to the original. Emit reciprocal `hreflang` alternatives including self, using only public, available, indexable variants; `x-default` points to an available fallback. Keep the set consistent after deletions and approval changes. Set document/article language and JSON-LD language/provenance consistently. Google's [localized-version guidance](https://developers.google.com/search/docs/specialty/international/localized-versions) supports self/reciprocal alternatives and an unmatched-language fallback. Validate SEO language values separately from the broader imported BCP-47 model.

Avoid reader-preference-dependent canonical or `hreflang` output. A multilingual release can use today's origin resolver until #123 is implemented, but must use one resolver and document the remaining host-alias duplication. That integration does not authorize implementing or closing #123 in this feature.

## Recommended decisions

Adopt one event per version and one required setup choice. Publish the active language by default, preserving private sources; make publishing both an explicit secondary action. Keep the writing target fixed and use the invoked version as reference. Provisionally use marked references with separate group/source semantics, subject to the interoperability spike; require mutual signed evidence for cross-signer grouping. Use one accessible language control, passive source-change hints and one retry action. Preserve metadata through Redaktion in the initial release, with one submission per language. Keep machine translation for a later explicit service flow. Publication coordination, source provenance and group resolution remain behind the ordinary writing workflow.
